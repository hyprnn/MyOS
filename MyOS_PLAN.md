# MyOS: план пути к настоящей ОС

Sep 28, 2026 · @iusearchbtw

MyOS уже живёт без прошивки; чтобы стать настоящей ОС, ей нужны десять этапов — от порядка в коде до запуска своих программ, файлов на диске и сети.

## Где мы сейчас

MyOS уже умеет главное, что отличает ОС от программы: после команды `ebs` она уходит от прошивки и работает на своих драйверах. Но всё это пока одна программа в одном файле, без процессов, без дисков и без защиты памяти.

| Уже есть | Чего не хватает до настоящей ОС |
| --- | --- |
| Выход из прошивки (ExitBootServices) | Свои таблицы страниц (виртуальная память) |
| Своя GDT, IDT, экран паники | Процессы и переключение задач |
| Таймер LAPIC 1000 Гц, калибровка по PIT | Прерывания от устройств (сейчас всё опросом) |
| Аллокатор страниц по карте памяти | Куча с мелкими блоками (kmalloc) |
| Свой xHCI: USB-клавиатура и мышь, PS/2 | USB-хабы, горячее подключение, флешки |
| Текстовая консоль шрифтом 8×16, GUI, Сапёр | Диски (SATA/NVMe) и настоящая файловая система |
| RAM-диск на 32 файла | Программы в пользовательском режиме (ring 3) |
| Один файл `main.c`, \~19 000 строк | Модули, нормальная сборка, отладочный лог |

## Этап 0 — порядок в коде

Один файл на 19 000 строк уже тормозит работу, а дальше кода будет в разы больше. Этот этап ничего нового не умеет, но без него все следующие будут идти вдвое дольше.

- [x] Разложить `main.c` по папкам: `kernel/` (память, прерывания, таймер), `drivers/` (xHCI, PS/2, PCI), `gui/`, `shell/`, `lib/` (строки, печать)
- [x] Makefile вместо `build.sh`: пересобирается только изменённое, `make run` сразу запускает QEMU
- [x] Отладочный лог в последовательный порт COM1: в QEMU он виден в терминале (`-serial stdio`), не нужны скриншоты
- [x] Свой `printf`-подобный вывод вместо цепочек `print` + `print_uint` + `print_hex`
- [x] git-репозиторий: каждый шаг — коммит, можно откатиться, можно сравнить «до/после»
- [x] Автотест в QEMU: скрипт загружает ОС, набирает `ebs`, `usb`, `mem` и проверяет лог — ловит поломки до того, как они дойдут до ноутбука

**Готово, когда:** `make run` собирает ОС из десятка файлов, всё работает как сейчас, а лог загрузки идёт в терминал.

**Размер:** небольшой, 1–2 сессии.

**Статус: выполнено 28 сентября 2026.** `main.c` разложен на 33 модуля + `myos.h`, сборка без единого предупреждения; `make test` проходит 8 проверок за \~10 секунд; история — в git (3 коммита). Заодно мышь теперь проверяет переход в boot protocol запросом GET\_PROTOCOL.

## Этап 1 — загрузчик + ядро и своя виртуальная память

Сейчас ОС — это UEFI-программа, которая сама себя вытаскивает из прошивки и живёт на её таблицах страниц. Настоящие ОС устроены иначе: маленький **загрузчик** (UEFI-программа) грузит с диска отдельный файл **ядра** (`kernel.elf`), отдаёт ему карту памяти и framebuffer и уходит. Ядро с первой инструкции не знает о прошивке ничего.

- [x] Загрузчик: читает `kernel.elf` с ESP, собирает «паспорт загрузки» (карта памяти, GOP, адрес ACPI), вызывает ExitBootServices и прыгает в ядро
- [x] Ядро в «верхней половине» адресного пространства (адреса вида `0xFFFFFFFF80000000`) — нижняя половина остаётся программам
- [x] Свои 4-уровневые таблицы страниц: код ядра — только чтение, данные — без исполнения (NX), вся RAM отображена одним куском, видеопамять — write-combining
- [x] Забрать в аллокатор память BootServicesCode/Data (сейчас её трогать нельзя — там таблицы прошивки и наш стек)
- [x] `kmalloc`/`kfree` с мелкими блоками (slab) вместо «целая страница на каждую аллокацию»
- [x] TSS с отдельным стеком для Double Fault и защитные страницы под стеками: переполнение стека — экран паники, а не перезагрузка
- [x] Обработчик Page Fault, который говорит, что именно случилось (чтение/запись, какой адрес, память ядра или нет)
- [x] Режим «без прошивки» становится единственным: команда `ebs` и прокладка `g_kst` больше не нужны

**Готово, когда:** ОС стартует сразу в режиме ядра, `mem` показывает почти всю RAM свободной, а запись в код ядра даёт понятный экран Page Fault.

**Размер:** большой — это фундамент всего остального.

**Статус: выполнено 28 сентября 2026.** Загрузчик `BOOTX64.EFI` (23 КиБ) читает `kernel.elf` (145 КиБ) и передаёт ему паспорт загрузки; ядро живёт по адресу `0xFFFFFFFF80000000` на своих таблицах страниц: код только для чтения, данные без исполнения, экран write-combining, NULL даёт Page Fault. В QEMU с 256 МиБ `mem` показывает 245 МиБ свободными, из них 39 МиБ забраны у прошивки и загрузчика. `crash write`, `crash null` и `crash stack` дают понятные экраны паники; `make test` проверяет это за 4 запуска. Таблица `g_kst` осталась внутренним интерфейсом ядра для шелла и GUI, прошивку она не вызывает; её заменят системные вызовы на этапе 6. На ноутбуке ещё не проверено.

## Этап 2 — ACPI и поиск железа

Сейчас адреса многих устройств мы угадываем (I/O APIC «обычно» на `0xFEC00000`). ACPI — это таблицы, в которых компьютер сам рассказывает, что у него есть и где; без них не заработают ни прерывания от устройств, ни второе ядро процессора, ни выключение кнопкой.

- [x] Найти RSDP (его адрес отдаёт UEFI в таблице конфигурации) и разобрать список таблиц XSDT
- [x] MADT: сколько ядер процессора, где I/O APIC, как старые IRQ (клавиатура, RTC) разведены по линиям
- [x] MCFG: современный доступ к PCIe через память (ECAM) вместо портов `0xCF8/0xCFC`
- [x] HPET: ещё один эталон времени на случай «мёртвого» PIT
- [x] FADT: выключение и перезагрузка своими силами, без RuntimeServices
- [x] Решить, чем исполнять AML (байт-код внутри ACPI — батарея, крышка ноутбука, кнопка питания): свой интерпретатор — годы работы, готовая библиотека uACPI — выходные (см. «Главные решения»)
- [x] Команда `acpi`: список таблиц, ядер, контроллеров прерываний

**Готово, когда:** `shutdown` выключает ноутбук через ACPI, а `acpi` показывает все ядра процессора и адрес I/O APIC из таблиц, а не угаданный.

**Размер:** средний (без AML); с AML — зависит от решения про библиотеку.

**Статус: выполнено 28 сентября 2026.** Ядро читает все таблицы ACPI с проверкой контрольных сумм; `acpi` показывает таблицы, ядра процессора, I/O APIC и переназначения IRQ из MADT, окно PCIe, HPET и порты питания. I/O APIC теперь берётся из MADT, а не угадывается; на чипсетах с MCFG конфигурация PCI идёт через ECAM (после сверки с портами). Частота TSC меряется по трём эталонам — HPET, PIT и таймеру ACPI PM; в QEMU они сходятся до 0,004%. `reboot` сначала пробует регистр сброса из FADT, `shutdown` ищет `_S5_` в DSDT и SSDT. **Решение по AML:** свой интерпретатор не пишем — когда понадобятся батарея, крышка и кнопка питания (этап 9), подключим uACPI. На ноутбуке ещё не проверено.

## Этап 3 — прерывания вместо опроса, USB-хабы и горячее подключение

Сейчас драйверы сами постоянно спрашивают устройства «есть что-нибудь?». В настоящей ОС устройство само дёргает процессор прерыванием — это и быстрее, и процессор может спать, пока ничего не происходит.

- [x] Разводка прерываний через I/O APIC (по данным из MADT): PS/2-клавиатура на IRQ 1
- [x] MSI/MSI-X для PCI-устройств: xHCI сам сообщает о новых событиях
- [x] Очередь событий ввода в ядре: обработчик прерывания кладёт, шелл и GUI забирают
- [x] USB-хабы (в том числе встроенные в ноутбук и в мониторы): устройства за хабом тоже работают
- [x] Горячее подключение: воткнул мышь после загрузки — она заработала; выдернул — драйвер это заметил
- [x] USB-флешки (Mass Storage, протокол Bulk-Only) — первый диск для этапа 5
- [x] Светодиоды CapsLock/NumLock на USB-клавиатуре

**Готово, когда:** в простое процессор занят почти на 0%, а мышь, воткнутая через USB-хаб после загрузки, сразу работает.

**Размер:** средний.

**Статус: выполнен (коммит 4c1a819).** Клавиатура и мышь работают по прерываниям: xHCI через MSI-X, PS/2 через I/O APIC (IRQ 1 и 12). В простое процессор спит в `hlt`, `cpu` показывает загрузку (в QEMU около 1,5%). Работают USB-хабы (дерево устройств, route string), горячее подключение и отключение на корневых портах и за хабом, USB-флешки (BOT + SCSI, команда `disk`), лампочки CapsLock/NumLock/ScrollLock на USB и PS/2, PS/2-мышь/тачпад с колёсиком. `make test` проверяет 8 сценариев, включая хаб с мышью и флешкой и подключение мыши во время работы. В QEMU нельзя проверить: Transaction Translator у USB 2.0-хабов, хабы USB 3 и SuperSpeed-флешки.

## Этап 4 — многозадачность

Сейчас ОС делает ровно одно дело: пока идёт `sleep 5`, не тикают часы и не двигается мышь. Многозадачность — это несколько потоков, между которыми таймер переключает процессор сотни раз в секунду.

- [x] Поток ядра: свой стек + сохранённые регистры; переключение контекста на ассемблере
- [x] Планировщик: сначала простой по кругу (round-robin), вытеснение по таймеру LAPIC
- [x] Сон и ожидание: `sleep` отдаёт процессор другим, поток ждёт клавишу без кручения в цикле
- [x] Замки (spinlock, mutex): два потока не ломают одну структуру данных
- [x] Вынести в отдельные потоки USB-драйвер, часы, отрисовку GUI
- [x] Команда `ps`: список потоков и сколько процессора ест каждый
- [x] Запуск остальных ядер процессора (SMP) — сделан на этапе 10

**Готово, когда:** во время `sleep 10` в терминале GUI часы идут, мышь двигается, а `ps` показывает несколько потоков.

**Размер:** большой (SMP — ещё один средний кусок).

**Статус: выполнен (коммит bb6fa59), кроме SMP.** Потоки ядра со своими стеками, переключение на ассемблере, планировщик с вытеснением по таймеру (квант 10 мс; только что проснувшиеся идут первыми, остальные по очереди — `threadtest` показывает 33/33/33%). `sleep` и паузы драйверов — настоящий сон, процессор в это время у других или в `hlt`. Замки: мьютекс (спящий), спин-замок, `kx_lock` со счётчиком у каждого потока. USB обслуживает отдельный поток `usb`, который будит прерывание контроллера. В терминале GUI `SLEEP N` и `SPIN N` работают в своём потоке: в заголовке окна идут часы, мышь двигается, `PS` показывает потоки. Команды `ps`, `threadtest`, `spin N`. Отдельными потоками сделаны USB и долгие команды GUI; часы и отрисовка GUI остались в цикле GUI — им хватает. Запуск остальных ядер (SMP) — не сделан, остаётся на потом.

## Этап 5 — диски и файловая система

Сейчас файлы живут в RAM и исчезают при перезагрузке. Настоящая ОС читает и пишет диск — и программы для этапа 6 тоже будут лежать на диске.

- [x] Слой «блочное устройство»: прочитать/записать сектор — одинаково для флешки, SATA и NVMe
- [x] Драйверы: AHCI (SATA-диски), NVMe (современные SSD), virtio-blk (быстрый диск в QEMU); какой диск в ноутбуке — покажет `lspci`
- [x] Таблица разделов GPT: найти на диске свой раздел
- [x] FAT32 на чтение и запись — её понимает и UEFI, и Linux, удобно подкидывать файлы с Arch
- [x] VFS — общий слой файлов: `open/read/write/close`, пути с папками, старый RAM-диск становится одной из файловых систем
- [x] Кэш секторов в RAM, чтобы не читать одно и то же постоянно
- [x] Команды `cd`, `mkdir`, `ls` с папками; Проводник в GUI видит диск

**Готово, когда:** файл, созданный в MyOS, переживает перезагрузку и читается из Arch.

**Размер:** большой. Запись на настоящий диск — сначала только на флешку или в QEMU: ошибка в драйвере может испортить установленный Arch.

**Статус: выполнен (коммит 5207454).** Блочные устройства: USB-флешки (теперь и запись), SATA через AHCI, NVMe; разделы MBR и GPT, флешки без таблицы разделов; кэш на 512 секторов со сквозной записью. FAT16 и FAT32 на чтение и запись, с длинными именами, как их пишет Linux. VFS: в корне `/` тома (`/ram` — старый RAM-диск, `/usb0p1`, `/sata0p1`, `/nvme0p1`), пути с папками, `open/read/write/close`. Команды `ls`, `cd`, `pwd`, `mkdir`, `rmdir`, `touch`, `cat`, `write`, `append`, `edit`, `cp`, `mv` (и между дисками), `rm`, `size`, `df`, `disk`; в приглашении видна текущая папка. Проводник в GUI ходит по всем томам (`E` на рабочем столе). **Безопасность:** внутренние диски ноутбука только читаются, писать можно лишь на USB-флешки и диски QEMU. Проверено в QEMU: файл, записанный на флешку, на месте после перезапуска; образы дисков проверяет независимый читатель FAT (`tools/fatimg.py`, аналог `fsck.fat`) — ошибок нет. virtio-blk не делали: тесты идут через AHCI и NVMe — те же драйверы, что нужны ноутбуку. exFAT, NTFS и ext4 пока не монтируются. *Позже (после этапа 8): exFAT — чтение и запись через библиотеку FatFs (флешки, раздел Ventoy).*

## Этап 6 — программы в пользовательском режиме

Это главная граница между «большой программой» и ОС: сейчас все команды вшиты в ядро, а ошибка в любой из них роняет всё. Дальше программы — отдельные файлы на диске, каждая в своей запертой памяти, и упавшая программа убивает только себя.

- [x] Кольцо 3 (ring 3): сегменты пользователя в GDT, переход в программу и обратно
- [x] Системные вызовы через инструкцию `syscall`: `write`, `read`, `open`, `exit`, `sleep`, дальше больше
- [x] Процесс = своё адресное пространство + один или несколько потоков из этапа 4
- [x] Загрузчик ELF: программа, собранная на Arch, запускается из файла
- [x] Мини-libc (`printf`, `malloc`, строки) и правила сборки программ под MyOS
- [ ] Шелл сам становится программой; команды `calc`, `edit`, Сапёр — переезжают из ядра в файлы
- [x] Падение программы: сообщение в шелле вместо экрана паники

**Готово, когда:** `hello` с диска печатает строку в ring 3, а нарочно сломанная программа завершается, а ОС работает дальше.

**Размер:** большой. После него MyOS — уже операционная система в полном смысле слова.

**Статус: выполнен (коммит fdadafd), кроме «шелл и Сапёр — программы».** Программы работают в ring 3, у каждой своя память (свои таблицы страниц), загрузчик ELF, 17 системных вызовов через `syscall` (`sysnum.h`), мини-libc (`printf`, `malloc`, строки) и правила сборки (`user/`). Программы `hello`, `calc` и `edit` (переехали из ядра), `guess`, `primes`, `crash`; лежат в `/bin` и на флешке в `\APPS\`. Упавшая программа завершается с понятным сообщением, `Ctrl+C` останавливает зависшую. В GUI — ярлыки на рабочем столе в пиксельном стиле Windows 95; ярлыки программ запускают их в терминале GUI. Старая команда ядра `crash` теперь `kpanic`. Шелл и Сапёр пока остаются в ядре: им нужен протокол окон этапа 7.

## Этап 7 — оконная система и графика

Сейчас GUI — одна большая функция с одним окном за раз и только заглавными латинскими буквами. Цель — настоящий рабочий стол, где каждое окно — отдельная программа из этапа 6.

- [x] Композитор: у каждого окна свой буфер, на экран перерисовываются только изменившиеся прямоугольники
- [x] Несколько окон сразу: перетаскивание мышью, фокус, панель задач со списком окон
- [x] Протокол «программа ↔ композитор»: создать окно, получить события мыши и клавиатуры (общая память + сообщения)
- [x] Шрифты с Юникодом, в том числе кириллица (у Spleen она есть); потом — сглаженные шрифты
- [x] Раскладки клавиатуры RU/EN с переключением
- [x] Настоящий курсор-стрелка, ускорение мыши, колесо, правая кнопка
- [ ] Стиль в духе Hyprn / Frutiger Aero — если хочется, тут самое место

**Готово, когда:** на экране два окна разных программ, их можно таскать, и в одном из них можно написать текст по-русски.

**Размер:** большой и бесконечный — красить можно вечно.

**Статус: выполнен (коммит a69fab7).** Композитор (`gui/wm.c`): у каждого окна свой буфер, кадр собирается в памяти, на экран идут только изменившиеся точки. Несколько перекрывающихся окон: перетаскивание за заголовок, фокус, крестик, панель задач с кнопкой «Пуск», кнопками окон, часами и индикатором раскладки. Окна у программ: `SYS_WIN_*`, буфер — общая память ядра и программы, события (клик, клавиша) в очереди окна; оконные программы Часы, Рисование, Жизнь (`user/apps/`). Шрифт сглаженный 8x16 с кириллицей, курсор-стрелка, колесо и правая кнопка. Раскладка EN/РУ (ЙЦУКЕН), переключение Ctrl+Space — в Блокноте можно писать по-русски. Родные окна: Терминал, Блокнот, Проводник, Сапёр, О системе. Не сделано: шелл и Сапёр как отдельные программы (пока это родные окна ядра) и стиль Hyprn/Frutiger Aero (пока классический Win95).

## Этап 8 — сеть

Сеть — это драйвер сетевой карты снизу и стек TCP/IP над ним. Проще всего начать с кабеля: Wi-Fi — одна из самых трудных вещей в любой ОС (прошивки чипов, шифрование WPA2).

- [x] Драйвер для QEMU: virtio-net или Intel e1000
- [x] Драйвер проводной карты ноутбука (модель уточнить по `lspci` в MyOS или Arch)
- [x] Стек по слоям: Ethernet → ARP → IPv4 → ICMP (ping) → UDP → DHCP (получить адрес от роутера) → DNS → TCP
- [x] Сокеты для программ из этапа 6
- [x] Команды `ifconfig`, `ping`, простой `wget` по HTTP
- [x] Решить: свой стек (учебная ценность) или готовый lwIP (быстрее и надёжнее)
- [x] Wi-Fi — 802.11-клиент с WPA2 (`net/wlan.c`) и драйвер Realtek RTL8821CE (`drivers/rtw8821c.c`, перенос rtw88); проверка на ноутбуке — по фото

**Готово, когда:** `ping 8.8.8.8` получает ответы, а `wget` скачивает страницу по HTTP.

**Размер:** большой (без Wi-Fi); Wi-Fi — очень большой.

**Статус: выполнен.** На ноутбуке RTL8821CE включается (прошивка, eFuse, RFE 2) и `wifi scan` находит сети 2,4 и 5 ГГц (26 сетей, в том числе скрытые и WPA3); `wifi connect` к домашней WPA2-сети — подключение, адрес по DHCP, `ping` в Интернет работает. **Решение: свой стек** (`net/`, без lwIP): Ethernet, ARP, IPv4, ICMP, UDP, DHCP, DNS и TCP — с повторами по таймеру (RTO по замерам), быстрым повтором, окном перегрузки, сборкой сегментов «не по порядку», пробами нулевого окна, listen/accept. Поток ядра `net` разбирает кадры и крутит таймеры; в простое спит. Интерфейс-петля `lo` (127.0.0.1). Сетевые карты: Intel e1000/e1000e (82540EM, 82574L — в QEMU; I217–I219 — по документации), Realtek RTL8111/8168, RTL8106E, RTL8169 (то, что стоит в HP 250 G7 — вслепую, в QEMU таких нет) и RTL8139C+ (QEMU); прерывания MSI или INTx с проверкой, иначе опрос. **USB-модем**: телефон в режиме «USB-модем» или USB-Ethernet-переходник (RNDIS, CDC-ECM, CDC-NCM) — интерфейс `usb0`, подключение и отключение на лету; это путь в Интернет с ноутбука без кабеля. Сокеты — обычные `fd` программ (11 новых системных вызовов). Программы `ping`, `ifconfig`, `nslookup`, `wget` (в том числе на флешку, переадресации, chunked), `nc`, `httpd` (веб-сервер), `nettest`; команда ядра `net`; адрес — на панели задач рабочего стола. `make test`: 15 запусков, в том числе загрузка с хоста 300 КБ с проверкой каждого байта (и с потерей каждого 10-го кадра), хост качает с `httpd` внутри MyOS, USB-модем RNDIS и ECM. **Wi-Fi:** `wifi scan` / `wifi connect сеть пароль` / `wifi disconnect` / `wifi debug`. 802.11-клиент `net/wlan.c` (поиск по каналам 2,4 и 5 ГГц, authentication, association, 4-стороннее и групповое рукопожатие WPA2, CCMP программно, переподключение, интерфейс `wlan0` с DHCP) проверен автотестом с программной точкой доступа (`wifi sim`: неверный пароль, DHCP широковещательным кадром через GTK, ping). Драйвер Realtek RTL8821CE `drivers/rtw8821c.c` — перенос Linux rtw88 (BSD-3-Clause) + прошивка Realtek в `firmware/`; в QEMU такого чипа нет — проверка на ноутбуке. Пока нет: WPA3-only, TKIP, 802.11n/ac (скорости до 54 Мбит/с). **HTTPS:** TLS 1.2 на готовой библиотеке BearSSL (MIT) в программах, проверка сертификатов по корням Mozilla, `wget https://...`. **На ноутбуке:** интернет через USB-модем телефона работает (`ping archlinux.org`), Wi-Fi — Realtek RTL8821CE.

## Этап 9 — реальное железо и повседневность

Этот этап — о том, чтобы MyOS можно было поставить на HP 250 G7 рядом с Arch и реально пользоваться. Многое из него идёт параллельно с другими этапами, как только появляется нужная основа.

- [x] Браузер (сделан раньше установки — по просьбе): полная libc (picolibc) + сокеты BSD и `poll`, curl с BearSSL, NetSurf в окне рабочего стола — HTML/CSS, картинки, кириллица, HTTPS
- [x] Установка на диск: `sudo tools/install-arch.sh` из Arch — папка `EFI/MyOS/` на разделе EFI + пункт меню systemd-boot `loader/entries/myos.conf` (файлы Arch не трогаются, `--remove` убирает). Свой раздел не нужен: MyOS целиком — два файла. Проверено в QEMU (systemd-boot -> MyOS); на ноутбуке — ждём проверки
- [ ] Тачпад: на ноутбуках это обычно I2C HID или PS/2 — тот же HID, что у USB-мыши, только по другой шине
- [x] Батарея, зарядка, крышка, кнопка питания — AML через библиотеку uACPI + свой драйвер контроллера EC; команда `battery`, значок заряда на панели задач; кнопка питания выключает машину (`_PTS` и S5 через uACPI). Проверено в QEMU (поддельная батарея — своя таблица SSDT); на ноутбуке — ждём проверки
- [x] Яркость экрана: регистры ШИМ подсветки видеокарты Intel (PCH — Core i3/i5; BXT — Celeron/Pentium Apollo/Gemini Lake), запасной путь — ACPI `_BCL/_BCM/_BQC`; команда `brightness`, клавиши Fn (Notify 0x86/0x87). В QEMU проверен путь ACPI; регистры Intel — только на ноутбуке
- [x] Настройки и Wi-Fi при запуске: `wifi save` пишет `EFI/MyOS/wifi.cfg` (имя сети + ключ PMK, не пароль) на том, с которого загрузились (он находится по пути и размеру ядра), — только по команде и только в эту папку; при загрузке MyOS подключается к запомненной сети в фоне; `wifi connect` без имени, `wifi forget`
- [ ] Сон при закрытии крышки (ACPI S3) — сложно, в самый конец
- [ ] Звук через Intel HD Audio
- [ ] Свой драйвер видеокарты — почти наверняка не нужен: framebuffer от GOP хватает для рабочего стола; смена разрешения — в загрузчике через GOP
- [ ] После каждого этапа — проверка на ноутбуке, а не только в QEMU (как показала история с мышью)

**Готово, когда:** MyOS загружается с диска ноутбука из меню загрузки, работают клавиатура, тачпад и мышь, виден заряд батареи.

**Размер:** большой, растянут по всему пути.

## Этап 10 — все ядра, программы вместо встроенных команд, мультимедиа

Порядок выбран так: Г → Д → В → А → Б → Е.

- [x] **Г. Все ядра процессора (SMP).** Трамплин запуска ядер (16→32→64 бита, INIT–SIPI), у каждого ядра свои GDT/TSS/стеки/таймер, данные ядра через регистр GS (swapgs на границе с программами). Большой замок ядра (ticket lock): программы идут на всех ядрах параллельно, код ядра ОС — на одном за раз; держатель пропускает ждущих вперёд раз в миллисекунду. Общий планировщик, у каждого ядра свой поток простоя, пробуждение спящих ядер межпроцессорным прерыванием. Команды `cpu` (ядра), `smptest` (замер ускорения). Проверено в QEMU (4 ядра: ускорение ~3,6×); на ноутбуке — ждём проверки
- [ ] **Д.** Шелл и команды (калькулятор, блокнот, Сапёр) — отдельные программы в ring 3
- [ ] **В.** Крышка ноутбука: закрыл — подсветка гаснет, открыл — загорается
- [ ] **А.** Звук Intel HD Audio: `play` WAV/MP3, громкость клавишами
- [ ] **Б.** DOOM (doomgeneric) со звуком
- [ ] **Е.** Стиль Frutiger Aero
- [ ] Потом: мелкие замки вместо большого — чтобы и код ядра ОС шёл на нескольких ядрах
